# AI 情報収集・提案画面 設計メモ

実装：`frontend/src/app/(main)/ai/page.tsx`・`frontend/src/app/(main)/records/[id]/page.tsx`。

- 対応ユースケース：[docs/ai/api/usecase.md](../api/usecase.md) UC-01・UC-02
- 対応API：[docs/ai/api/request-response.md](../api/request-response.md) / [docs/ai/api/endpoints.md](../api/endpoints.md) / [docs/ai/api/error.md](../api/error.md)
- パス：`/ai`（`docs/design.md` P07）。学習記録詳細画面（`/records/{id}`、P05）からも生成できる
- 目的：ユーザーの興味・直近の学習記録・または特定の学習記録をもとにWeb検索を行い、要約と参考リンクをまとめた参考資料を生成する

---

## 全体レイアウト（`/ai`）

```
┌──────────────────────────────────────────┐
│ AI 情報収集・提案                          │
│ ※ 入力内容はAIによる分析のため OpenAI 社・Web検索サービスに送信されます │
│ [ 例：バックエンドを伸ばしたい（任意）_____ ] │
│                      [参考資料を生成する]   │
├──────────────────────────────────────────┤
│ <iframe>（生成された要約HTMLを表示）        │
│ 参考リンク一覧                             │
├──────────────────────────────────────────┤
│ 別途、学習記録としても残したい場合           │
│ 内容：     [ 要約からの抜粋・編集可______ ] │
│ 学習時間： [ 5 ] 分（編集可）                │
│ タグ：Spring Security（既存 or 新規作成される）│
│                        [学習記録をつける]   │
├──────────────────────────────────────────┤
│ 保存済みの参考資料      タグで絞り込み：[すべて▼]│
│ ┌─────────────┐ ┌─────────────┐          │
│ │Spring Security│ │Docker        │  ← カード │
│ └─────────────┘ └─────────────┘          │
└──────────────────────────────────────────┘
```

学習記録には独立したタイトル欄が無い（内容欄のみ）ため、生成結果にもタイトル欄は無い。「学習記録をつける」フォームの内容欄の初期値は「interest（またはタグ名）＋要約の抜粋」。

---

## 生成の操作（`POST /api/ai/references`）

- 「興味のある技術・分野」を入力する任意の1行テキスト（`interest`、200文字以内。空欄可）と、ボタン「参考資料を生成する」
- 押すと `{ interest }`（未入力なら省略）を `POST` する
- レスポンスに`jobId`が入っていれば、`GET /api/ai/jobs/{jobId}`のポーリングを開始する（後述「状態パターン」参照）
- レスポンスに`jobId`が無く`message`だけある場合（学習記録0件かつinterest未入力）は、そのメッセージをそのまま表示する
- ポーリング完了（`status: DONE`）後、`result`（要約HTML・参考リンク一覧・分類先のタグ）を表示する

### キャッシュはしない

- サーバー側で結果をキャッシュしない。「生成する」を押すたびに新しい参考資料が生成される
- コストの上限は結果のキャッシュではなく、レート制限（1日10回）で担保する
- フロントの TanStack Query 側は「叩くとコストが発生するか」で自動発火の可否を分けている
  - コストが発生する2つ → 自動発火させない
    - 生成リクエスト（`POST /references`）：`useMutation`（`src/hooks/useAiMutations.ts`の`useGenerateReference`）
    - 結果のポーリング（`GET /jobs/{jobId}`）：`useQuery`（`useAiJob`）だが、`jobId`が来るまでは動かないよう制御
  - コストが発生しない1つ → 自動発火して問題ない
    - 保存済み一覧の取得（`GET /references`）：`useQuery`（`useAiReferences`）

### レート制限

- 1ユーザー1日10回まで（Redisのカウンタ（`INCR`＋`EXPIRE`）で判定するため複数台構成でも正しく機能する）
- 超過すると `429`。表示メッセージ例：「本日のAI利用上限、または処理中のリクエストの上限に達しました。しばらくしてから再度お試しください」
- 同じユーザーが未完了ジョブを持ったまま連打した場合も `429`。ボタンを生成中 disabled にすれば通常は起きない

## 学習記録詳細画面からの生成（`recordId`指定）

```
┌──────────────────────────────────────────┐
│ ← 戻る          [この記録について参考資料を作る] [編集] [削除] │
└──────────────────────────────────────────┘
```

- `/records/{id}`（学習記録詳細画面）にボタンを追加。押すと`POST /api/ai/references`に`recordId`（その記録のID）を渡してリクエストする
- 受付成功時は`/ai?jobId=...`へ遷移し、`/ai`側がURLの`jobId`を読み取って最初からポーリングを始める（もう一度ボタンを押させない）
- この記録の内容は、検索クエリの組み立て・OpenAIへのプロンプトの両方で最優先の材料として使う。直近の学習記録一覧は背景情報として別枠で併用する
- `recordId`を指定した場合、学習記録の件数や`interest`の有無にかかわらず必ずジョブが作られる（「学習記録0件のとき固定メッセージ」の分岐は`recordId`未指定のときだけ）

## タグ分類の表示

- 既存タグ（大文字小文字を無視した名前一致）に一致した場合：そのタグ名をそのまま表示する
- 一致しなかった場合：「◯◯（新規作成されます）」のように表示する。**この時点ではタグはまだ作成されていない**
- 「学習記録をつける」を押した瞬間に、未作成のタグであれば`POST /api/tags`でタグを作成してから`POST /api/learning-records`を呼ぶ。タグの新規作成をAIの非同期ジョブ側で行わない理由は[../api/usecase.md](../api/usecase.md)の「タグ分類の扱い」参照

---

## 保存済み参考資料一覧（タグ絞り込み）

- `/ai`画面の下部に、`GET /api/ai/references`で取得した過去の参考資料をタグ・生成日時のカード一覧で表示する
- タグでの絞り込みセレクトを画面上に置き、選択すると`GET /api/ai/references?tag={tagId}`を呼び直して一覧を絞り込む（`docs/learning-records/screen/overview.md`のダッシュボードにあるタグ絞り込みと同じ考え方）
- カードをクリックすると、その参考資料をiframeで開く（生成直後の画面と同じ表示・同じ「学習記録をつける」導線を使う）

## 入力・バリデーション（`docs/ai/api/error.md` と対応）

| チェック | 内容 |
|---|---|
| クライアント側 | `interest` は200文字超で入力自体を止める（`maxLength`）。生成中はボタンを disabled |
| サーバー側 | `interest`が禁止パターン・有害コンテンツと判定された場合 → 400「入力内容に不適切な部分が含まれているか、内容が長すぎます」 |
| レート制限 | 429 → 上限メッセージ。`FAILED` → 「現在AIサービスが利用できません。しばらく経ってから再度お試しください」 |
| `recordId`不正 | 404（存在しない場合と他人の記録である場合を区別しない） |

- クライアント側の事前フィルタはしない（禁止語リストをフロントに持たせるとバレて回避されやすくなるため、サーバー側だけで判定する）

## 状態パターン

非同期化（SQS）により、「ボタンを押す→即結果」ではなく「ボタンを押す→受付→ポーリング→結果」という状態遷移になる。実装は`src/hooks/useAiMutations.ts`の`useAiJob`（`refetchInterval`で2秒ごとにポーリングし、`DONE`/`FAILED`になったら止める）。

```
初期（未生成）
  → 結果エリアに何も表示しない

生成中（ボタンを押した直後〜完了まで）
  → POST が 202 + jobId を返した時点でこの状態に入る
  → ボタンを「生成中...」にして disabled
  → 「AIが検索・要約しています（数秒〜1分ほどかかることがあります）」を表示
  → GET /api/ai/jobs/{jobId} を2秒間隔でポーリングする

成功（status: DONE）
  → ポーリングを止め、result を表示する

失敗（status: FAILED）
  → ポーリングを止め、message を表示する
```

- ポーリング間隔・タイムアウトの目安：OpenAI呼び出しはタイムアウト30秒＋リトライ1回（間隔2秒）で最悪約62秒かかる（[guardrail-design.md の2・3](../guardrail-design.md#2-タイムアウト設定)。Web検索の時間は別途かかる）
- 非同期化により、この待ち時間はHTTP接続を占有する形では発生しないため、axios自体のリクエストタイムアウトは通常の短い値のままでよい

## 使用API

| 操作 | API |
|---|---|
| 参考資料生成（受付） | `POST /api/ai/references`（`{ interest?, recordId? }`）→ `202` + `jobId`、または即`message` |
| 生成結果のポーリング | `GET /api/ai/jobs/{jobId}` |
| 保存済み参考資料一覧 | `GET /api/ai/references`（`?tag={tagId}`で絞り込み） |
| 学習記録をつける | `POST /api/tags`（タグ未作成の場合のみ）→ `POST /api/learning-records` |
