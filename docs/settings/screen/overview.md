# 設定画面 設計メモ

- 対応ユースケース：[docs/settings/api/usecase.md](../api/usecase.md) UC-01〜03
- パス：`/settings`（`docs/design.md` の画面一覧に既定義）
- 目的：ログインユーザーが自分のプロフィール（メールアドレス・表示名・作成日時）を確認し、表示名とパスワードを変更できるようにする

---

## 画面構成

1画面の中に「プロフィール」「パスワード変更」の2セクションを縦に並べる（タブや別ページには分けない。項目数が少なく、切り替える意味がないため）。**各セクションは自分専用の保存ボタンとフォームを持ち、他のセクションと保存単位が分離されている**（GitHub の Settings、Vercel、Linear、Notion など多くのSaaSプロダクトで共通のパターン）。1つの巨大なフォームにしないのは、「パスワード欄の入力ミスで、変えたかっただけの表示名まで保存できない」という体験の悪さを避けるため。バリデーションルールも全く別物（表示名は文字数、パスワードは現在パスワードとの一致確認）なので、フォームを分けた方が実装もシンプルになる。

```
┌──────────────────────────────────────┐
│ 設定                                    │
├──────────────────────────────────────┤
│ プロフィール                              │
│  メールアドレス   test@example.com         │
│  表示名          [テストユーザー______] [保存]│
│  登録日          2026-01-10               │
├──────────────────────────────────────┤
│ パスワード変更                             │
│  現在のパスワード [______________]         │
│  新しいパスワード [______________]         │
│                            [変更する]      │
└──────────────────────────────────────┘
```

## 表示項目

- 初回表示時に `GET /api/users/me` を叩き、結果を各項目に流し込む
  - メールアドレス（`email`）：読み取り専用。入力欄にしない（`docs/settings/api/overview.md` の通り本APIでは変更不可のため、編集できるように見せない）
  - 表示名（`displayName`）：編集可能なテキスト入力
  - 登録日（`createdAt`）：読み取り専用。`2026-01-10` の形式（時刻は表示しない）

## プロフィール（表示名変更）

### 操作

- 表示名の入力欄1つ＋「保存」ボタン
- 取得した `displayName` を入力欄の初期値にする。ページ読み込み時にすでに値が入っている状態からスタートする（空欄から入力させない）
- 「保存」を押すと `PATCH /api/users/me` を送信する

### レスポンス

- 更新後のプロフィール全体（`docs/settings/api/request-response.md` の形）が返るので、そのまま画面の表示を更新する。特に `email` と `createdAt` は変わらないが、レスポンスをそのまま使えば個別に気にする必要がない

## パスワード変更

### 操作

- 「現在のパスワード」「新しいパスワード」の2つの入力欄＋「変更する」ボタン
- どちらもマスク表示（`type="password"`）
- 「変更する」を押すと `PUT /api/users/me/password` を送信する

### 成功後の重要な注意（トークン失効）

- `docs/settings/api/request-response.md` の通り、パスワード変更に成功すると **操作した本人の端末も含めて** そのユーザーの全リフレッシュトークンが Redis 上で失効する
- そのため、成功レスポンスを受け取った直後にこの画面のフロントが何もしないと、次にアクセストークンの期限（15分）が切れた瞬間、リフレッシュに失敗してログイン画面に飛ばされる（`frontend/src/lib/api.ts` の401リフレッシュ処理が失敗するルート）
- これを利用者に「突然ログアウトされた」と感じさせないため、パスワード変更成功時にフロント側で以下のどちらかを行う
  - a. 新しいパスワードでそのまま `POST /api/auth/login` を呼び直し、新しいトークンペアを取得して `authStore` を更新する（画面を移動させず「パスワードを変更しました」を出すだけで済む）
  - b. 「パスワードを変更しました。再度ログインしてください」と表示し、`clearAuth()` した上で `/login` に遷移させる
  - 本アプリでは a を採用する（利用者の操作を1回減らせるため）。実装時に `useUpdatePassword` の `onSuccess` 内で `login()` を呼び、返ってきた `accessToken` / `refreshToken` で `authStore` を上書きする

### 成功後のフォームの扱い

- 入力欄2つはクリアする（次に来た人や見返したときに平文パスワードが残らないようにする）
- 「変更しました」のトースト/インライン成功表示を出す

## 入力・バリデーション（`docs/settings/api/error.md` と対応させる）

| 操作 | クライアント側チェック | サーバーエラー→表示 |
|---|---|---|
| 表示名変更 | 空文字なら「保存」を無効化、100文字超で入力時にカウンタ表示 | 400 →「表示名は1〜100文字で入力してください」をフォーム直下に表示 |
| パスワード変更 | 新しいパスワードが8〜72文字でなければ「変更する」を無効化。どちらかが空でも無効化 | 400（8文字未満・72文字超・現在と同一）→ 該当メッセージをフォーム直下に表示。403（現在のパスワード不一致）→「現在のパスワードが正しくありません」を現在のパスワード欄の下に表示 |

- クライアント側で「新しいパスワードが現在のパスワードと同一」まではチェックしない（現在のパスワードは平文のまま画面に保持していないため比較できない。サーバーの400を待って表示する）

## 状態パターン

- 初回ロード中：プロフィールセクションをスケルトン表示（他画面と揃える）。パスワード変更セクションは入力欄自体は表示してよい（他データに依存しないため）
- 表示名保存中／パスワード変更中：それぞれのボタンを disabled にして二重送信を防止（loginページの `isSubmitting` と同じパターン）
- パスワード変更失敗（403）：入力欄はクリアしない（打ち直しの手間を減らす）。表示名変更の成功・失敗とは独立に扱う（2つのフォームは別々に送信できる）

## 使用API

| 操作 | API |
|---|---|
| プロフィール取得 | `GET /api/users/me` |
| 表示名変更 | `PATCH /api/users/me`（`{ displayName }`） |
| パスワード変更 | `PUT /api/users/me/password`（`{ currentPassword, newPassword }`） |
| パスワード変更成功後の再ログイン | `POST /api/auth/login`（`docs/auth/api/request-response.md`） |

## ナビゲーション：アカウントメニュー（アバター＋ドロップダウン）に載せる

- 現状のヘッダー（[`(main)/layout.tsx`](../../../frontend/src/app/(main)/layout.tsx)）は「ダッシュボード」「タグ管理」というフラットなリンクの横に、独立した「ログアウト」ボタンが並んでいるだけ
- 設定を追加するにあたり、フラットな `NAV_ITEMS` にただ「設定」を並べるのではなく、**右上にアバター（イニシャルの丸アイコン）を置き、クリックするとドロップダウンで「設定」「ログアウト」が出る**形にする
  - 理由：「学習記録・タグ管理」のような**アプリの本体機能**と、「設定・ログアウト」のような**アカウント操作**は性質が違う。GitHub・Vercel・Linear・Notion など多くのSaaSがこの2つを視覚的に分離しており（本体機能は横並びのnav、アカウント操作は右上のアバターメニュー）、慣れているユーザーほど「アカウント関連は右上を見ればある」という前提で操作する。「一般的なSaaSの設定への導線」を踏襲する
  - 実装コスト：shadcn/ui にまだ `dropdown-menu` と `avatar` が入っていない（[`components/ui/`](../../../frontend/src/components/ui/)を参照。現状 badge/button/card/dialog/form/input/label/skeleton/textarea のみ）。`npx shadcn@latest add dropdown-menu avatar` の追加が必要
  - アバターの中身：画像は扱わないので、`displayName` の先頭1文字を丸背景に白文字で表示する（`AvatarFallback`）

```
┌──────────────────────────────────────────┐
│ ダッシュボード   タグ管理              (テ)▾ │ ← (テ) = displayName の頭文字。クリックでメニュー
├──────────────────────────────────────────┤     ┌────────┐
│                                            │     │ 設定    │
│                                            │     │ ログアウト│
└──────────────────────────────────────────┘     └────────┘
```

- 影響範囲：本画面の実装とセットで [`(main)/layout.tsx`](../../../frontend/src/app/(main)/layout.tsx) の改修が必要。既存の「フラットなnav＋独立ログアウトボタン」から「nav＋アカウントメニュー」への置き換えになる
